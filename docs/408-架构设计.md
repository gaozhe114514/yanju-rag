## 1. 在线链路（对应 fig1）

```
提问
 → ① 接入层（Nginx 限流 / FastAPI 编排 / 日志 / 成本记账）
 → ② Query 理解（意图分类 · 指代消解 · 术语归一）   [DeepSeek + 规则回退]
 → ③ 双路召回：BM25（应用内 bigram）+ 向量（pgvector + bge-small-zh-v1.5），各 top-50
 → ④ RRF 融合 → top-30
 → ⑤ 精排 Rerank（bge-reranker-v2-m3）→ top-5
 → ⑥ 拒答闸门（分数绝对值 + top1/top2 margin + 必含术语）→ 不通过则拒答 + 写缺口日志
 → ⑦ 生成（DeepSeek-V3，强制 JSON：结论 + 引用 + 原文片段）
 → ⑧ 引用校验（引用片段必须是 chunk 原文子串）→ 不过则重试 1 次 → 降级为「资料未覆盖」
 → ⑨ 组装响应（答案 + 引用 + 页码锚点 + 耗时/成本）
 → ⑩ 前端渲染（KaTeX / 引用高亮 / 点击跳原文）
```

## 2. 分层架构（对应 fig2）

| 层 | 组件 | 说明 |
|---|---|---|
| 客户端 | Web 响应式 | 手机浏览器直接可用，砍掉 App |
| 接入层 | Nginx + FastAPI | TLS、限流、鉴权、日志、成本记账 |
| 应用服务 | 问答编排 / 考频图谱 / 错题归因 / 反馈缺口 | 四个 API，先做前两个 |
| 检索层 | BM25 · pgvector · RRF · Reranker · 引用定位 | 检索是准确率主战场 |
| 模型层 | bge-small-zh-v1.5 · bge-reranker-v2-m3 · DeepSeek-V3 | 见下节选型理由 |
| 存储层 | **PostgreSQL 16 + pgvector**（已实现）· Redis / 对象存储（未接） | 一个库起步，别过早拆 |
| 离线管线 | 真题 PDF → LLM 抽取 → 人工校对 → 打标 → 切分建索引 | 人工校对是必须的 |

## 3. 选型表：为什么是它

| 位置 | 选择 | 为什么不选另一个 |
|---|---|---|
| 向量库 | **pgvector** | 数据量只有几千 chunk，Qdrant/Milvus 是过度设计；pgvector 和业务表同库，能一条 SQL 做过滤（按科目/年份/知识点），省一个服务 |
| 关键词检索 | **应用内 BM25 Okapi** | 实测 pg 的 `simple` 配置对中文近乎无效，zhparser 要编译扩展、还要维护词典；几百个 chunk 的 BM25 用纯 Python 毫秒级算完，没必要搬进数据库。数据量到十万级再考虑 ES |
| Embedding | **bge-small-zh-v1.5** | 512 维、CPU 可跑，2C4G 服务器上能把首响压在十几秒；设计稿里的 bge-m3 更强但 2.2GB，本地 CPU 反而拖慢整体延迟。换 bge-m3 时只需改 `KB_EMBED_DIM=1024` 并重建向量 |
| 精排 | **bge-reranker-v2-m3** | 408 是「一字之差」密集型，Cross-Encoder 是刚需。别用 LLM 直接打分（贵且不稳定） |
| 生成 | **DeepSeek-V3** | 中文强、便宜、支持 JSON 模式；Qwen-Max 作备选做 A/B |
| 轻任务 | **Qwen2.5-7B-Instruct** | 意图分类/改写这类任务不需要大模型，小模型省一半钱、快一倍 |
| 融合 | **RRF** | 不用分数加权：BM25 与余弦相似度量纲不同，按排名融合更稳 |
| 拒答 | **阈值 + 规则** | 不用 LLM 判断「该不该答」：多一次调用、多一份不稳定，且无法解释 |

## 4. 数据模型（实际落地）

```sql
chunks
  id, kind(question|knowledge), year, seq, subject, chapter, title
  search_text         -- 浏览页搜索用（小写合并文本）
  text                -- 召回与引用正文：题干+选项 / 考点卡片
  answer, analysis
  payload jsonb       -- 原始 JSONL 行，浏览接口直接下发
  related_question_ids text[]  -- 考点 → 题目双向关联
  embedding vector(512)
  updated_at

meta         -- corpus_fingerprint / embedding_model / embedding_dim
gap_logs     -- id / query / reason / top_chunk / top_score / created_at
answer_cache -- cache_key / query / payload jsonb / created_at
```

设计稿里的 `kp`、`qa_log`、`eval_item` 仍是规划：知识点现在是 `knowledge` 类型的 chunk（带 subject/chapter，没有父子树）；请求日志先由 Nginx access log 承担；评测集是文件（`data/eval/*.jsonl`），还没有入库。

**硬约束**：一道题 = 一个 chunk（题干 + 选项 + 答案 + 解析 + 图），不切开。

## 5. 三个必须能辩护的设计决策

1. **为什么双路召回而不是纯向量**
   纯向量对「根本政治制度 / 基本政治制度」这类一字之差的表述召回不稳；BM25 + 领域词典兜住精确匹配，向量兜住口语化提问。

2. **为什么要有独立的引用校验环节**
   prompt 里写「必须引用」不等于模型真的引用了原文。用「引用片段是否为 chunk 原文子串」做程序化校验，是把「相信模型」换成「验证模型」，这一步是拒答率之外最能讲的技术点。

3. **为什么拒答阈值要靠评测集扫出来**
   拍脑袋定 0.6 的阈值在面试里一问就穿。正确做法：200 条评测集（A 资料内可答 / B 资料外 / C 跨知识点），扫阈值画曲线，选 B 类拒答率高且 A 类误拒率低的点，并报出这两个数。

## 6. 成本与容量

- 单次问答：rerank（约 5 条 × 长文本）+ 生成（约 2k token 输入） ≈ **0.005–0.02 元**
- 日 500 次问答 ≈ 3–10 元/天
- 服务器：2C4G 足够（模型全走 API），约 60–100 元/月
- 缓存：同一 query 的答案缓存 24h（`KB_CACHE_TTL`，0 关闭），命中率通常 15–25%，直接省这部分成本；只缓存作答成功的回答，拒答不缓存
