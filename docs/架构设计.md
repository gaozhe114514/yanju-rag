# 言据 · 架构设计

> 目标：让每个结论都能被读者自己验证；答不出来就明说，不硬编。
> 范围：通用 Agent + 可引用知识库。Web 优先，不做 App、支付与社区。

## 1. 在线链路

```
用户提问
  │
  ├─ plan（独立问题 / 追问改写）
  ├─ agent（原生函数调用，最多两轮）
  │
  ├─ 直接回答
  ├─ kb_overview / 天气 / 时间 / 计算 / 代码 / 搜索 / 网页正文
  └─ search_kb
        │
        ├─ BM25（进程内）
        ├─ 向量召回（pgvector，bge-small-zh-v1.5）
        ├─ RRF 融合
        ├─ Cross-Encoder 精排（bge-reranker-v2-m3，CPU）
        ├─ 拒答闸门（最低分 + 分差）
        ├─ 生成（DeepSeek，强制 JSON）
        ├─ 引用逐字校验（quote 必须命中原文，≥10 字）
        ├─ 失败：换查询重试一次
        └─ 仍失败：拒答，并写缺口日志
```

Agent 由 LangGraph 编排，模型通过原生函数调用选择工具；工具循环最多两轮，引用校验与拒答仍是硬约束。

## 2. 分层架构

| 层 | 模块 | 职责 |
|---|---|---|
| 前端 | `web/index.html` | 单文件、hash 路由、SSE 流式、四套主题；桌面与手机同一套页面 |
| API | `api/app.py` | HTTP 接口、账号、权限、限流、缺口与反馈；统一出口 |
| Agent | `agent/` | 原生函数调用循环、工具注册、状态图、线程记忆（内存 / Postgres checkpoint） |
| 回答 | `answer/` | 拒答闸门、prompt、生成、逐字校验、缓存、表格统计、创作 |
| 知识库 | `kb/` | 默认库、公司库、个人库；文件解析、OCR、切分与片段管理 |
| 检索 | `retrieval/` | 中文 bigram BM25、bge 向量、RRF、词面 / Cross-Encoder 精排 |
| 存储 | `db/` | PostgreSQL + pgvector：知识库、文档、片段、账号、缓存与日志 |

## 3. 选型与理由

| 选型 | 当前实现 | 理由 |
|---|---|---|
| 关系库 + 向量 | PostgreSQL 16 + pgvector | 一个库同时存业务数据与向量，备份、权限、事务都统一 |
| 中文 BM25 | 应用内 BM25 Okapi | 中文 FTS 要 zhparser，2C4G 上多一个扩展不划算；几百到几万片段内存完全够 |
| 向量模型 | bge-small-zh-v1.5（512 维） | 全 CPU 可跑，延迟可控；换 bge-m3 只改环境变量并重建向量 |
| 精排 | bge-reranker-v2-m3 | 中文资料里「一字之差」很常见，Cross-Encoder 明显提升 top1；CPU 上只精排 10 个候选 |
| 生成 | DeepSeek，强制 JSON | 输出结构固定，引用校验才能机器判；没有 key 时退到抽取式 mock，链路可离线跑 |
| Agent | LangGraph | 路由、工具、有界重试和线程记忆用状态图表达最清楚；节点本身不依赖框架，单测不用拉起图 |
| 前端 | 单文件，无构建 | 部署只要一个静态文件；交互复杂度用原生 JS 控制，避免为了构建而构建 |
| 文件进料 | 本地解析 + 本地 OCR | 不存原文件，解析后只留文本与片段，省掉对象存储与外部解析服务 |

## 4. 数据模型

```
collections          知识库：id / 名称 / 说明 / 可见性 / 归属
  documents          文档：标题、原文、状态、sha256
    doc_chunks       片段：seq / 正文 / 向量 / start_off / end_off / revision
    document_versions 编辑历史
    document_assets  插图与附件（按字节存）
collection_members   公司库成员：editor / viewer

users / user_sessions / user_data   账号、会话、跨设备同步
gap_logs / answer_feedback / answer_cache / request_logs   拒答、反馈、缓存、请求日志
```

- 默认知识库是内置只读库，启动时从 `data/curated/default/` 灌入；未登录可读。
- 公司库登录后全员可读，写权限由管理员、建库人或被指定的成员持有。
- 个人库只有建库人可见，管理员也看不到。
- BM25 不落库：进程启动/库变化时按 `doc_chunks` 构建，向量召回走 pgvector。

## 5. 三个必须能辩护的设计决策

1. **引用逐字校验，不通过就拒答。** 生成模型不可信；引用必须能在原文里逐字找到，否则这条结论不算数。校验失败换查询重试一次，仍失败就拒答，绝不降级成「大概是这样」。
2. **资料没覆盖就明说。** 缺口日志记录问题、原因和最高分片段；产品上宁可少答，也不编。
3. **Agent 只做编排，不碰事实。** 路由决定「聊 / 查 / 用工具」，事实仍来自检索到的原文与工具返回；引用和拒答规则在 Agent 之外，任何路径都不能绕过。

## 6. 成本与容量

- 线上 2C / 3.7G：FastAPI + PostgreSQL + Nginx，模型全 CPU。
- 单次问答：检索 + 精排约 1.5–7 秒（取决于语料与是否精排），生成取决于模型；缓存命中直接返回。
- 向量维度 512，片段量在十万级以内用 HNSW 足够；再大再考虑分区或专用向量库。

## 7. 后续
