# 存储层（PostgreSQL + pgvector）

线上只有一个数据库服务，不做过度拆分：

| 表 | 内容 |
|---|---|
| `collections` | 知识库：名称、说明、可见性（builtin / shared / private）、归属、每库切片参数 `chunk_target` / `chunk_overlap` |
| `documents` | 文档：标题、原文、状态、sha256、字符数、文件夹 `folder`、标签 `tags` |
| `collection_folders` | 真正的文件夹树：`collection_id` + 路径 `制度/人事`；空文件夹也保留 |
| `document_files` | 上传的原始文件字节（bytea），用于服务重启后继续解析与失败重试 |
| `ingest_jobs` | 解析任务：状态、尝试次数、错误；启动时把 queued / running 的任务重新排队 |
| `kb_audit_logs` | 知识库操作日志：操作人、动作、对象、时间；不记正文与请求头 |
| `wiki_pages` | 自动 Wiki 页面：标题、摘要、正文、来源片段 id、是否手改、版本号 |
| `wiki_page_versions` | Wiki 编辑历史；恢复旧版也写一条新版本 |
| `wiki_entities` | Wiki 实体：人物 / 部门 / 产品 / 概念 / 组织，带别名与来源片段 |
| `wiki_links` | Wiki 关系边：内链 / 共用来源，带权重 |
| `doc_chunks` | 片段：`collection_id` / `document_id` / seq / 正文 / `vector(512)` / 原文起止偏移 / `revision` |
| `document_versions` | 整篇编辑历史 |
| `document_assets` | 插图与附件（按字节存） |
| `collection_members` | 公司库成员：editor / viewer |
| `users` / `user_sessions` / `user_data` | 账号、会话、跨设备同步副本 |
| `gap_logs` | 拒答日志：query / 原因 / top1 命中 / 分数 |
| `answer_cache` | 应答缓存；只存作答成功的回答 |
| `answer_feedback` | 回答反馈：是否有帮助、差评原因、备注、引用 id |
| `request_logs` | 请求日志：方法、路径、状态、耗时、问句（不含 IP / UA） |

- 默认知识库是内置只读库，启动时从 `data/curated/default/` 灌入；公司库与个人库的读写权限在 `api/access.py` 判。
- 向量召回是 `ORDER BY embedding <=> query LIMIT k`，按 `collection_id` 过滤；HNSW 索引在 `doc_chunks.embedding` 上。
- BM25 不落库：库变化时按 `doc_chunks` 在进程内重建索引。中文 FTS 要 zhparser 一类扩展，2C4G 上不划算；数据库负责存储、过滤和向量检索，关键词召回交给应用。
- 没有 `DATABASE_URL` 时知识库状态退到 `data/work/kb/library.json`，只适合本地开发；原始文件与解析任务的续跑只在 Postgres 模式下保证。
- 原始文件放 Postgres bytea 是为了少一个组件：单库上限 500MB，原型与实习演示够用。以后文件量大了再换 MinIO / S3 一类的对象存储，数据库只留元数据。

## Agent 线程记忆

配了 `DATABASE_URL` 且装了 `langgraph-checkpoint-postgres` 时，API 启动会调用 `PostgresSaver.setup()`，在同一个库里额外建 `checkpoints` / `checkpoint_blobs` / `checkpoint_writes` / `checkpoint_migrations`。它们只存 Agent 线程状态（最近 20 条消息、本轮检索上下文、工具调用与校验轨迹）；建表失败会自动退回进程内 `InMemorySaver`，`/health` 的 `agent_checkpointer` 会显示 `postgres` 还是 `memory`。

删除对话时不会同步删 checkpoint；需要清空时单独 `TRUNCATE checkpoints, checkpoint_blobs, checkpoint_writes`，不影响知识库与缓存。

## 为什么现在不用 MinIO / S3

MinIO 和 S3 都是**对象存储**：把文件按「桶 + 对象名」整块存起来，通过 HTTP 读写，适合图片、PDF、音视频这类大文件。S3 是 AWS 的接口标准，MinIO 是能在自己服务器上跑的兼容实现；阿里云 OSS、腾讯云 COS 也提供兼容 S3 的接口。

本项目现在把上传的原始文件直接放 PostgreSQL 的 `document_files` 表（bytea），原因是：

- 只有一份数据，备份、迁移、权限都不用再维护第二套系统；
- 单篇上限 20MB、单库上限 500MB，2C / 3.7G 的演示机放得下；
- 解析任务与原始文件在同一个事务边界里，重启续跑简单。

什么时候该换：文件总量到几十 GB、需要多人并发上传大文件、要给文件做 CDN 或预签名下载时，再把 `document_files` 换成 MinIO / S3，数据库只留 `document_id` 和对象 key。业务代码已经通过 `save_document_file` / `get_document_file` 收口，替换时不用动 API 和前端。
